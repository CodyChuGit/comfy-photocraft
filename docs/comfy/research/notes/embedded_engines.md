# Embedded native engines for in-process DiT inference from a Rust desktop app (RTX 5090, Windows) — state as of 2026-10-16

Scope: ONNX Runtime (pykeio/ort) with CUDA / TensorRT / TensorRT-RTX EPs; NVIDIA TensorRT 10.x/11.x and TensorRT-RTX directly; libtorch via tch-rs; stable-diffusion.cpp (ggml) and diffusion-rs; llama.cpp for Qwen3-VL. Target models: Qwen-Image-Edit-2511 (~20B), Krea 2 / FLUX-class (~12B), Qwen-Image-2.1, SAM 3 / 3.1, Qwen3-VL 4B.

All sizes below were either measured by me on 2026-10-16 (HTTP HEAD on download.pytorch.org, PyPI JSON API, pypi.nvidia.com HEAD) or quoted from the cited page. Wheel/zip sizes are compressed download sizes; on-disk is larger (unknown factor, not measured).

Version landscape observed on 2026-10-16 (GitHub releases API): stable-diffusion.cpp `master-968-8cd731e` (2026-10-15); llama.cpp `b11696` (2026-10-16); NVIDIA/TensorRT `v11.4` (2026-10-09); microsoft/onnxruntime `v1.31.0` (2026-10-09); pykeio/ort `v2.0.0-rc.14` (2026-10-12); tch crate 0.26.0 (crates.io, 2026-08-23); TensorRT-RTX 1.7 (docs "latest", PyPI stub `tensorrt-rtx 1.7.1.116` uploaded 2026-10-14).

## Q1. Is there a proven path for Qwen-Image-Edit-2511 or FLUX-class DiTs through ONNX Runtime or TensorRT on consumer Blackwell? Who did it and at what speed?

### Takeaway
FLUX.1-dev is proven on TensorRT on an RTX 5090: NVIDIA's own demoDiffusion (TensorRT 10.8+) runs it in FP4 at 3.85 s/image (30 steps, end-to-end) with 11.1 GB VRAM in low-VRAM mode. There is **no first-party or widely-reported ONNX/TensorRT path for Qwen-Image, Qwen-Image-Edit (any version), or Krea 2** — the only proven sub-16-bit path for Qwen-Image-Edit on a 5090 is Nunchaku (SVDQuant NVFP4), a PyTorch/CUDA extension, not an FFI-embeddable engine. Pure ONNX Runtime (CUDA EP, no TensorRT) has no published FLUX/Qwen DiT deployment; one 2026 ORT issue shows FlashAttention not even dispatching for DiT-style attention.

### Cited Findings
- NVIDIA blog (2025-05-14): FLUX.1-dev end-to-end, 30 steps, RTX 5090 — FP16 10,930.96 ms (low-VRAM mode required), FP8 6,680.93 ms, FP4 3,852.75 ms; RTX 4090 FP8 10,620.37 ms for comparison. FP4 fully-connected layers "up to 3.1x the performance of FP8" (layer level). Built with TensorRT 10.8 (demoDiffusion release/10.8), ONNX 1.18.0 for FP4 export, ModelOpt v0.27. FP4 PTQ degraded small text; NVIDIA recovered quality with distillation-based QAT from a BF16 teacher. — [NVIDIA Developer Blog: TensorRT unlocks FP4 image generation for Blackwell GeForce RTX 50 series](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/)
- Same blog, FLUX pipeline VRAM (default → `--low-vram`): FP16 39.3 → 23.9 GB; BF16 35.7 → 23.9 GB; FP8 24.6 → 14.9 GB; FP4 21.67 → 11.1 GB. — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/)
- NVIDIA mentions "custom NVIDIA NIM nodes for ComfyUI (Comfy-Org/NIMnodes)" integrating TensorRT FLUX engines into ComfyUI. — [NVIDIA Developer Blog](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/)
- TensorRT demoDiffusion (branch release/10.13, tested with TensorRT 10.13.0.35) supports: SD1.5/2.1, SDXL, SD3, SD3.5 (medium/large, BF16/FP8), SVD, Stable Cascade, FLUX.1-dev / FLUX.1-schnell txt2img (FP16, BF16, FP8, FP4), FLUX.1-dev img2img (BF16/FP8), FLUX.1 ControlNet depth/canny (BF16/FP8/FP4). **FLUX Kontext and Qwen-Image are not listed.** "FP8 and FP4 are supported on Hopper, Ada, and Blackwell" for FLUX; "The FP4 pipeline is most performant on Blackwell devices." FLUX FP16 native ONNX export needs >48 GB VRAM — use `--download-onnx-models` (pre-exported BF16/FP8/FP4). FLUX LoRA via `--lora-path`; "INT8/FP8 quantization does not work with LoRA weights." — [NVIDIA/TensorRT demo/Diffusion README (release/10.13)](https://github.com/NVIDIA/TensorRT/tree/release/10.13/demo/Diffusion)
- ONNX Runtime issue #27983 (opened 2026-04-05, closed): "Flash Attention not dispatched for DiT-style attention pattern (diffusion transformers)". — [microsoft/onnxruntime#27983](https://github.com/microsoft/onnxruntime/issues/27983) (found via GitHub issue search on 2026-10-16)
- The only FLUX-on-ONNX-Runtime artifact I found is a community model: TensorStack "Flux_schnell-f16-onnx", "optimized with Olive for DirectML", intended for the C# OnnxStack library. No official Microsoft Olive FLUX recipe found; Microsoft's Olive DirectML example covers SD 1.4/2 only. — [HF TensorStack/Flux_schnell-f16-onnx](https://huggingface.co/TensorStack/Flux_schnell-f16-onnx/commit/dbdef8e25e390c7b71a67e739aa19f28b6734f38); [microsoft/Olive DirectML SD example](https://github.com/microsoft/Olive/blob/main/examples/directml/stable_diffusion/README.md)
- Searching "Qwen-Image TensorRT ONNX export" returned only NVIDIA TensorRT-Edge-LLM pages about Qwen *VL* vision towers (Qwen3.5-0.8B / Qwen2.5-VL export), nothing about the Qwen-Image DiT. — [TensorRT-Edge-LLM quick start](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/getting_started/quick-start-guide.html)
- Nunchaku (MIT Han Lab SVDQuant): reports its NVFP4 FLUX model "3.1x faster than both BF16 and NF4 on the RTX 5090"; NVFP4 checkpoints "require an NVIDIA Blackwell GPU"; a Nunchaku NVFP4 transformer + NF4 text encoder generates a 1024x1024 image in ~1.7 s on an RTX 5090 with ~12 GB peak (vs ~24 GB BF16). Third-party guides list Qwen-Image / Qwen-Image-Edit among supported models. — [nunchaku-ai/nunchaku](https://github.com/nunchaku-ai/nunchaku); [MIT Han Lab SVDQuant NVFP4 blog](https://hanlab.mit.edu/blog/svdquant-nvfp4); [HF blog: Nunchaku in Diffusers](https://huggingface.co/blog/nunchaku-diffusers); [digitalcreativeai guide, Qwen-Image-Edit-2511 + Nunchaku](https://www.digitalcreativeai.net/en/post/how-speed-up-qwen-image-edit-2511-nunchaku-forge-neo)
- A community (non-Nunchaku, ComfyUI) Qwen-Image-Edit-2511 NVFP4 checkpoint on an RTX 5090, 832x1280, 4 steps: 2.52 it/s, "Prompt executed in 3.45 seconds", vs ~1 s/it for FP8 in the same test; author notes rough calibration. — [HF ANXS1/Qwen-Image-Edit-2511-NVFP4](https://huggingface.co/ANXS1/Qwen-Image-Edit-2511-NVFP4)
- TensorRT 11.4 support matrix: "compute capability SM 7.5 or higher"; the architecture filter lists 12.0 only as "NVIDIA RTX PRO 6000 Blackwell" and 12.1 as DGX Spark / Windows-on-ARM DLA; GeForce RTX 50 is not named explicitly. FP4 footnote: supported "in hardware emulation mode" on architectures without FP4 hardware. Built with CUDA 13.4 update 1; Windows 10/11 x64, Server 2022, Windows 11 Arm64. — [TensorRT support matrix (latest = 11.4)](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)
- ONNX Runtime TensorRT EP docs: first run "can be very long because building engine involves exhaustive profiling"; SD UNet session creation 384 s (no cache) → 42 s (timing cache) → 9 s (engine cache) → 1.9 s (embedded engine). Options `trt_engine_cache_enable`, `trt_timing_cache_enable`, `trt_engine_hw_compatible` (Ampere+ portable engines). Page still states ORT 1.22 / TensorRT 10.9 / CUDA 12.0–12.8 as "latest", i.e. it is stale relative to ORT 1.31. — [ORT TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html)
- ComfyUI_TensorRT community node: engine builds "roughly 3 to 10 minutes for image models", SVD 10–25 min, SVD-XT up to an hour; Flux listed as supported, no Flux-specific time. — [RunComfy node page](https://runcomfy.com/comfyui-nodes/ComfyUI_TensorRT); [InstaSD node docs](https://www.instasd.com/comfyui/custom-nodes/comfyui_tensorrt)

### Inferences
- For a FLUX-class 12B DiT the TensorRT route is real and NVIDIA-maintained, but it is a *Python* pipeline (demoDiffusion + ModelOpt) that produces engines; a Rust app would consume the resulting `.engine`/ONNX via FFI, and you cannot do the FP4 export on the user's machine (ONNX export needs >48 GB VRAM; pre-exported FP4 ONNX files are FLUX-specific and shipped by NVIDIA). Krea 2 is FLUX-architecture-derived but has no NVIDIA pre-exported ONNX, so an FP4/FP8 TensorRT Krea 2 engine would require you to run ModelOpt quantization yourself (unverified feasibility).
- Qwen-Image-Edit-2511 (~20B) has no ONNX/TensorRT precedent at all; the only measured fast path on a 5090 is NVFP4 inside PyTorch/ComfyUI (Nunchaku, or community NVFP4 checkpoints). Embedding it natively today means either sd.cpp GGUF (see Q2) or keeping ComfyUI.
- Expect TensorRT engine build for a 12–20B DiT on a consumer card to be tens of minutes on first run; the only concrete number I have is 384 s for an SD1.5 UNet via ORT, and 3–10 min for SD/SDXL engines in ComfyUI_TensorRT. Scale to 12–20B is unmeasured.

### Gaps
- No published end-to-end TensorRT (or ONNX Runtime) benchmark for Qwen-Image / Qwen-Image-Edit (any version) or Krea 2 on any GPU was found.
- No FLUX TensorRT engine *build time* number for RTX 5090 was found.
- Whether NVIDIA's pre-exported FLUX FP4 ONNX (`--download-onnx-models`) is licensed for redistribution inside a third-party app: not checked.
- demoDiffusion in the current TensorRT 11.x branch (release/11.4) was not fetched; model list above is from release/10.13.

## Q2. stable-diffusion.cpp: FLUX, Qwen-Image, Qwen-Image-Edit support? CUDA performance on 50-series? FP8/FP4?

### Takeaway
stable-diffusion.cpp (MIT) is the only embeddable engine that already runs every target image model: FLUX.1 dev/schnell, FLUX.1-Kontext, FLUX.2, Krea2, Qwen Image, Qwen Image 2.1, Qwen Image Edit original/2509/2511 (2511 needs `--model-args qwen_image_zero_cond_t=true`), Qwen Image Layered, Z-Image, with GGUF q4/q5/q8 and LoRA. It consumes FP8 (e4m3) safetensors by converting to INT8 (cuBLAS INT8 GEMM on CUDA); it has no NVFP4/FP4 compute path. No RTX 5090 or sd.cpp-vs-ComfyUI benchmark was found.

### Cited Findings
- Supported image models (README, news item dated 2026/10/16): SD1.x/2.x, SDXL, SD3/3.5, FLUX.1 (dev/schnell), FLUX.2 (dev/klein), FLUX.3 Image Klein (day-0, 2026-10-16), Chroma, Qwen Image, Qwen Image 2.1, Z-Image, Krea2, HiDream-O1-Image, PixArt, and many more; image editing: FLUX.1-Kontext-dev, Qwen Image Edit series, LongCat Image Edit, etc.; video: Wan2.1/2.2, LTX-2.x, HunyuanVideo 1.5. Backends: CPU (AVX/AVX2/AVX512), CUDA, Vulkan, Metal, OpenCL, SYCL. Inputs: .ckpt/.pth/.pt, safetensors, GGUF. "LoRA support, same as stable-diffusion-webui"; LCM/LCM-LoRA. Flash Attention, VAE tiling, TAESD. License MIT. No mention of Blackwell/sm_120. — [leejet/stable-diffusion.cpp README](https://github.com/leejet/stable-diffusion.cpp)
- Qwen Image Edit doc: supports original, 2509 and **2511**; 2511 requires `--model-args qwen_image_zero_cond_t=true` ("image editing quality will degrade significantly" otherwise). GGUF sources: QuantStack (original, 2509), unsloth/Qwen-Image-Edit-2511-GGUF (2511). Example files: `Qwen_Image_Edit-Q8_0.gguf`, `Qwen-Image-Edit-2509-Q4_K_S.gguf`, `qwen-image-edit-2511-Q4_K_M.gguf`; text encoder Qwen2.5-VL-7B (safetensors or mradermacher GGUF Q8_0 + mmproj for 2509). Shared flags: `--cfg-scale 2.5 --sampling-method euler --flow-shift 3 --offload-to-cpu -r <ref image>`. No VRAM, speed or LoRA notes on the page. — [docs/qwen_image_edit.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/qwen_image_edit.md); [docs/edit.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/edit.md)
- Qwen Image doc: diffusion GGUF from QuantStack/Qwen-Image-GGUF, VAE and text encoder from Comfy-Org/Qwen-Image_ComfyUI; example `qwen-image-Q8_0.gguf` + `Qwen2.5-VL-7B-Instruct-Q8_0.gguf`, 1024x1024, `--flow-shift 3 --offload-to-cpu`. No speed/VRAM/FP8/Lightning-LoRA notes. — [docs/qwen_image.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/qwen_image.md)
- Quantization doc: `--type` accepts f32, f16, q8_0, q5_0, q5_1, q4_0, q4_1; weights "are automatically converted when loading"; pre-convert with `sd-cli -M convert ... --type q8_0`. SD1.x 512x512 memory with FA: f32 ~2.4G, f16 ~1.9G, q8_0 ~1.6G, 4/5-bit ~1.5G. No bf16/K-quant/FP8 statement on this page (K-quant GGUFs are nonetheless used in the Qwen-Edit examples). — [docs/quantization_and_gguf.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/quantization_and_gguf.md)
- FP8 handling (issue #1929, opened 2026-09-01, closed 2026-09-27 via PR #2071): sd.cpp converts FP8 weights to INT8 (`GGML_TYPE_I8` + f32 scale/bias); on CUDA INT8 matmul runs natively via cuBLAS INT8 GEMM (`CUBLAS_COMPUTE_32I`) with custom quantize/dequantize kernels; on HIP the path was compiled out (fixed by #2071). — [leejet/stable-diffusion.cpp#1929](https://github.com/leejet/stable-diffusion.cpp/issues/1929)
- Issue #2139 (2026-10-14, closed): "core dump in CPU backend if using FP8 (e4m3) tensors" — confirms FP8 e4m3 tensors are a supported input type. Issue #1927 (2026-08-31, open): request to add FP8 (e4m3) for MiniMax-H3 on Vulkan/ROCm. — [#2139](https://github.com/leejet/stable-diffusion.cpp/issues/2139); [#1927](https://github.com/leejet/stable-diffusion.cpp/issues/1927)
- Open CUDA correctness issues relevant to target models: #1488 (2026-05-12, open) "Z-Image Base GGUF checkpoints produce blank white images in CUDA builds"; #2050 (2026-09-24, closed) "Qwen-Image-2.1: CUDA VAE decode leaves a white block on bright highlights"; #1949 (2026-09-08, closed) GGUF tensor-name truncation breaking Krea2. — [#1488](https://github.com/leejet/stable-diffusion.cpp/issues/1488); [#2050](https://github.com/leejet/stable-diffusion.cpp/issues/2050); [#1949](https://github.com/leejet/stable-diffusion.cpp/issues/1949)
- Issue #1869 (2026-08-11): community tested "Spectrum, Block Cache, SageAttention2, and ConvRot GGML implementations" for sd.cpp — indicates attention-kernel acceleration is still being contributed, not built in. — [#1869](https://github.com/leejet/stable-diffusion.cpp/issues/1869)
- Performance doc: `--flash-attn on|off|auto` saves ~600 MB for Flux at 768x768; `--conv-direct`; `--offload-to-cpu` keeps weights in system RAM and "does not reduce generation speed" (page's claim); `--offload-to-cpu --max-vram -1` recommended for the largest model a card can host; `--params-backend disk` option. No timing numbers. — [docs/performance.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/performance.md)
- PR #1062 (2025-12-07, merged) "Add compute kernels to Windows CUDA build" — relevant to which sm targets the official Windows CUDA binaries embed (contents not read). Third-party prebuilt `sd-cli` binaries exist that explicitly include sm_120 for RTX 50 and embed sm_120 PTX. — [leejet/stable-diffusion.cpp#1062](https://github.com/leejet/stable-diffusion.cpp/pull/1062); [HF decntai/sd-cli](https://huggingface.co/decntai/sd-cli)
- diffusion-rs (EricLBuehler, MIT): supports only FLUX.1 Dev/Schnell (DDUF, quantized DDUF); CUDA/Metal/AVX; GGUF 2–8 bit and bitsandbytes fp4/nf4/int8; LoRA and CPU+GPU offloading listed as *upcoming*; 84 commits, 130 stars. — [EricLBuehler/diffusion-rs](https://github.com/EricLBuehler/diffusion-rs)
- Only Flux-on-5090 speed found is ComfyUI, not sd.cpp: FLUX.1 dev 1024x1024 28 steps fp8 3.4 it/s on 5090 vs 2.2 it/s on 4090 (unverified blog with date inconsistencies). — [convly.ai](https://convly.ai/rtx-5090-vs-rtx-4090-for-ai-2026/)

### Inferences
- sd.cpp is the only candidate covering Qwen-Image-Edit-2511, Qwen-Image-2.1, Krea 2, FLUX and Z-Image today, with GGUF Q4/Q8 and LoRA, and a permissive licence with zero NVIDIA-redistribution questions beyond the CUDA runtime (it links cudart/cuBLAS). Its ceiling is precision: 4-bit is GGUF block-quant dequantized to FP16 compute (no NVFP4 tensor-core math), FP8 is INT8 GEMM, so it will not match TensorRT FP4 on FLUX (3.85 s) or Nunchaku NVFP4 on a 5090; the actual gap is unmeasured.
- Rapid churn (master-968 releases, day-0 model adds, open CUDA correctness bugs on Z-Image) means pinning a commit and running a per-model regression image set is mandatory.
- For Rust, binding sd.cpp means writing/maintaining your own bindgen FFI (no maintained Rust crate was found; diffusion-rs is a separate candle-based project limited to FLUX.1).

### Gaps
- No sd.cpp benchmark on RTX 5090 (or any Blackwell) for FLUX or Qwen-Image was found; no sd.cpp-vs-ComfyUI same-hardware comparison was found.
- Whether official sd.cpp Windows CUDA release binaries include sm_120 SASS (vs. relying on PTX JIT) — PR #1062 not read in detail.
- Qwen-Image-Edit-2511 VRAM at Q4_K_M/Q8_0 in sd.cpp on 32 GB — not documented; the docs always pass `--offload-to-cpu`.
- Z-Image CUDA blank-image bug (#1488) still open as of 2026-10-16 — status for Z-Image Turbo vs Base unclear.

## Q3. TensorRT-RTX status: ops for DiTs, JIT engine build times, Windows redistribution size

### Takeaway
TensorRT-RTX is at 1.7 (docs updated 2026-10-15), supports SM 7.5+ with Blackwell 12.0/12.1 and lists FP8 and "FP4 GEMM" among precisions, ships for CUDA 12.9u1 and CUDA 13.4, and is sold as "<200 MB" with JIT engine builds "in seconds"; the matching ONNX Runtime plugin EP (`onnxruntime-trt-rtx` 1.23.2) is a 77.8 MB wheel. No DiT/diffusion model is mentioned anywhere in its docs, and no published FLUX/Qwen TensorRT-RTX result exists; a Windows user in the ort tracker measured it 2–3x slower than DirectML on their (unspecified) model.

### Cited Findings
- Product page: SDK "engineered to be lean at under 200MB"; 1.0 release notes frame this as smaller download/disk footprint for consumer apps. 1.0 added Windows ML native acceleration. — [developer.nvidia.com/tensorrt-rtx](https://developer.nvidia.com/tensorrt-rtx); [1.0 release notes](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/getting-started/release-notes-1/1.0.html)
- Support matrix (latest): "supports NVIDIA hardware with compute capability SM 7.5 or higher"; architectures listed: 12.1 and 12.0 (Blackwell), 8.9 (Ada), 8.6 (Ampere), 7.5 (Turing); default engines portable across 8.6/8.9/12.0/12.1, Turing needs a device-specific build. Precision filter: FP32, FP16, BF16, INT8 WoQ GEMM, INT4 WoQ GEMM, FP8, FP4 GEMM (no per-architecture mapping in the page text). FP8 conv/matmul need 4-byte alignment; FP8 deconv unsupported. x86-64 packages for CUDA 12.9 Update 1 and CUDA 13.4. — [TensorRT-RTX support matrix](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/getting-started/support-matrix.html)
- 1.7 release notes: build example `--computeCapabilities=120`; "Engine build time reduced for all model architectures on Linux and Windows"; weights offloading (unload/restore an inactive engine's weights without rebuild); null weight placeholders for weight-stripped builds; "Improved fused multi-head attention (FMHA) fusion patterns"; fixed causal-mask accuracy in the Attention APIs; Edge-LLM speculative decoding backend. Known issues: `NonMaxSuppression`, `NonZero`, `Multinomial` unsupported; Windows only WDDM (TCC fails); `cudaMallocAsync` default can fail in CiG mode; "Engines are not forward-compatible" (rebuild on runtime upgrade); runtime cache files >~100 MB add serialization overhead; CPU-only AOT can be slower than on-device compile. Windows DLL named `tensorrt_rtx_1_7.dll`. API lifetime: 1.7 APIs kept until 10/2027. Diffusion models not mentioned. — [TensorRT-RTX 1.7 release notes](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/getting-started/release-notes-1/1.7.html)
- Install guide: Windows zip contains core library + ONNX parser DLLs with import libs, headers, samples, Python bindings, `tensorrt_rtx.exe` CLI, "licensing and open-source acknowledgments"; DLLs are signed; wheel `tensorrt_rtx-1.7.0.0-cp311-none-win_amd64.whl`; PyPI name `tensorrt-rtx` (CLI not included). Zip size not stated. — [Installing TensorRT-RTX](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/installing-tensorrt-rtx/installing.html)
- PyPI `tensorrt-rtx` 1.7.1.116 (uploaded 2026-10-14) is an sdist stub (0.0 MB) that redirects to NVIDIA's index; my HEAD scan of `pypi.nvidia.com/tensorrt-rtx/` found no `win_amd64` wheel link on that listing (so the real Windows wheel size is unmeasured). — [PyPI JSON for tensorrt-rtx](https://pypi.org/pypi/tensorrt-rtx/json) (measured 2026-10-16)
- ONNX Runtime TensorRT RTX EP: standalone plugin implementing the plugin-EP ABI "introduced in ONNX Runtime 1.23.0"; "just under 200 MB"; targets "Ampere and later (GeForce RTX 30xx and above)"; JIT builds hardware-optimized engines on end-user devices, said to take seconds; cached engines portable across RTX GPUs. — [NVIDIA TensorRT-RTX-EP-ABI docs](https://nvidia.github.io/TensorRT-RTX-EP-ABI/introduction.html)
- ONNX Runtime 1.23.0 added the TensorRT RTX EP plus a plugin-based EP API and Windows on-demand EP download. — [onnxruntime 1.23.0 release notes mirror](https://newreleases.io/project/pypi/onnxruntime/release/1.23.0)
- Measured: `onnxruntime_trt_rtx-1.23.2-*-win_amd64.whl` = 77.8 MB (uploaded 2025-12-01). — [PyPI onnxruntime-trt-rtx](https://pypi.org/project/onnxruntime-trt-rtx/) (PyPI JSON API, 2026-10-16)
- ort issue #532 (2026-02-12, closed "not planned"): in the Windows CU12 prebuilt (DirectML+CUDA+TensorRT+NVRTX), `onnxruntime_providers_nv_tensorrt_rtx.dll` depended on `nvinfer_10.dll`, i.e. a >3 GB full TensorRT install, because combining TensorRT and NVRTX makes the build use `nvonnxparser`; standalone NVRTX avoids it. Reporter also measured NVRTX "2–3 times slower than DirectML on their model". — [pykeio/ort#532](https://github.com/pykeio/ort/issues/532)
- TensorRT-RTX licence: NVIDIA TensorRT RTX License (21 Apr 2025) grants a "limited, non-exclusive, revocable, non-transferable, and non-sublicensable" licence to install/use, modify sample code, and "distribute it as part of an application", with conditions that the application has "material functionality beyond the included portions", only your application accesses the distributable portions, and modified sample code carries NVIDIA attribution. An August 2025 EULA PDF also exists (the PDF would not text-extract for me). — [NVIDIA_TensorRT_RTX_License_(21Apr2025).pdf](https://developer.download.nvidia.com/licenses/NVIDIA_TensorRT_RTX_License_(21Apr2025).pdf); [eula-12Aug2025.pdf](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/_static/eula-12Aug2025.pdf)

### Inferences
- TensorRT-RTX is the right *size class* for an installer (~200 MB vs ~1.9–2.1 GB for full TensorRT 11.4 libs on Windows) and it declares FP8 and FP4 GEMM on Blackwell, but every public example and all of NVIDIA's own tooling for it is LLM/CNN/Windows-ML oriented; there is no evidence anyone has run a 12–20B DiT through it. "Seconds" JIT claims are for small client models; a 20B DiT is untested.
- Engines are not forward-compatible across TensorRT-RTX runtime versions, so an app must rebuild caches on every engine update — plan for a cache-invalidation story.

### Gaps
- Exact byte size of `tensorrt_rtx_1_7.dll` + parser DLL on Windows: not found (NVIDIA says "<200 MB" for the SDK).
- Supported-operator list for transformer ops (LayerNorm, RMSNorm, GELU, RoPE-style Gather/Mul chains, Attention) — the operators reference page was not fetched; 1.7 notes mention FMHA fusion and Attention APIs only.
- Whether FP4 GEMM in TensorRT-RTX accepts ModelOpt-exported NVFP4 ONNX (as TensorRT 10.8+ does) — not documented in fetched pages.
- Any JIT build-time measurement for a model >1B parameters — none found.
- Exact wording of the 12 Aug 2025 EULA (PDF streams not extractable here; no HTML copy found — the 1.2 docs SLA URL 404'd).

## Q4. libtorch 2.x on Windows with CUDA 12.8/13: size, AOTInductor for custom DiTs, tch-rs upkeep

### Takeaway
libtorch Windows CUDA zips are 1.8–3.7 GB compressed (measured 2026-10-16): 2.11.0+cu130 = 1.89 GB, 2.11.0+cu128 = 2.65 GB, 2.13.0+cu130 = 3.53 GB, 2.14.x+cu130 = 3.66 GB. tch-rs is actively maintained (0.26.0 on 2026-08-23; README master targets libtorch v2.13.0) but pins one exact libtorch version per release. ### Inferences
- libtorch is the heaviest redistributable of all options (1.9–3.7 GB compressed, and it bundles cuDNN/cuBLAS inside the zip), and every tch release forces a libtorch bump; an app would pin e.g. tch 0.26 ↔ libtorch 2.13 (verify exact pair before shipping) and ship exactly that zip's `lib/*.dll`.

## Q6. Which redistributable pieces are legally bundleable by an MIT/Apache app, and how big is each?

### Takeaway
CUDA runtime libs, cuDNN runtime DLLs, TensorRT runtime DLLs and TensorRT-RTX may all be redistributed *inside* an application in object-code form under NVIDIA's SDK licence family (conditions: material additional functionality, only your app accesses them, consistent end-user terms, no standalone redistribution), but the NVIDIA SDK agreement (TensorRT and cuDNN supplements) forbids using the SDK "in a way that makes it subject to an open source license" (§2.5) — so the NVIDIA DLLs must be shipped as separately-licensed binaries, not under the app's MIT/Apache terms. Measured Windows sizes: cuDNN 9.27 cu12 708.6 MB / cu13 416.3 MB; cuBLAS cu12 527.5 MB; TensorRT 11.4 libs cu12 2,145.8 MB / cu13 1,863.6 MB; onnxruntime-gpu 1.31 160.3 MB; onnxruntime-trt-rtx 77.8 MB; libtorch cu130 1.9–3.7 GB; TensorRT-RTX "<200 MB" (NVIDIA claim).

### Cited Findings
**Licences**
- CUDA Toolkit EULA: §1.1.1 you may distribute the portions identified as distributable "incorporated in object code format" into an application; §1.1.2 "Your application must have material additional functionality, beyond the included portions of the SDK"; "The distributable portions of the SDK shall only be accessed by your application"; distribution terms must be consistent with the Agreement and protect users' privacy/security/legal rights; must notify NVIDIA of suspected non-compliant distribution; §1.2 "you may not distribute or sublicense the SDK as a stand-alone product". Attachment A lists distributable components incl. CUDA Runtime (cudart), cuBLAS/cuBLASLt, cuFFT, cuSPARSE, cuSOLVER, cuRAND, NPP, nvJPEG, NVRTC, NVVM, nvJitLink, libdevice, CUPTI, NVTX. Attachment B: bundled third-party components (Thrust Apache-2.0, etc.) keep their own notices. — [CUDA Toolkit EULA](https://docs.nvidia.com/cuda/eula/index.html)
- cuDNN: "LICENSE AGREEMENT FOR NVIDIA SOFTWARE DEVELOPMENT KITS" + cuDNN Supplement, both "v. February 22, 2022"; distributable = "the runtime files .so and .dll"; object code only, incorporated into an application; material added functionality; only your application accesses; notice "This software contains source code provided by NVIDIA Corporation" for modified samples; your terms must be consistent with the Agreement; §2.5 prohibits using the SDK in a way that makes it "subject to an open source license, such as requiring source disclosure or free redistribution"; §2.2 no sublicensing/distribution except as expressly provided; Critical Applications restrictions (§2.6/2.7); applications only for systems with NVIDIA GPUs. — [cuDNN EULA](https://docs.nvidia.com/deeplearning/cudnn/latest/reference/eula.html)

- TensorRT-RTX SDK "<200 MB" (NVIDIA claim; Windows DLL byte size not measured). — [developer.nvidia.com/tensorrt-rtx](https://developer.nvidia.com/tensorrt-rtx)
- ort's issue #532 characterises a full TensorRT install as "over 3 GB" on disk. — [pykeio/ort#532](https://github.com/pykeio/ort/issues/532)

### Inferences
- Computed installer budgets (compressed, CUDA 13 line; cuBLAS cu13 not measured so cu12 figure used): ORT CUDA EP stack ≈ 160 + 416 (cuDNN) + ~528 (cuBLAS) + 191 (cuFFT) + 66 (cuRAND) + 73 (NVRTC) + 3 (cudart) ≈ **1.4 GB**; adding TensorRT 11.4 cu13 libs ≈ **3.3 GB**; ORT + TensorRT-RTX EP instead ≈ 160 + 78 + <200 ≈ **<0.45 GB** plus whatever CUDA runtime pieces TensorRT-RTX needs (unverified); libtorch cu130 2.11 ≈ **1.9 GB** (2.14: 3.7 GB) all-in; sd.cpp CUDA ≈ its own DLL (tens of MB, unmeasured) + cudart + cuBLAS ≈ **~0.55 GB**.
- Legal pattern for an MIT/Apache app: ship NVIDIA DLLs as third-party binaries with NVIDIA's licence text in the installer, keep the app's own code MIT/Apache, do not claim the DLLs are covered by the app licence, and make sure only the app loads them (no public "plugin SDK" exposing them). §2.5 is the clause to run past counsel: it targets making the *SDK* subject to copyleft-style obligations, not merely co-shipping with permissively licensed code, but NVIDIA has not published guidance on that reading (no source found).
- Alternative that sidesteps all NVIDIA redistribution: download the CUDA/cuDNN/TensorRT wheels or NVIDIA installers at first run from NVIDIA's own servers (what the `onnxruntime-gpu[cuda,cudnn]` extras and ONNX Runtime's Windows on-demand EP download do) — then the user, not the app, receives them under NVIDIA's terms. Sizes above are then first-run download times instead of installer bloat.

### Gaps
- Uncompressed on-disk sizes for every package — not measured.
- `nvidia-cublas-cu13` Windows wheel size — not queried.
- Whether TensorRT-RTX requires cuBLAS/cuDNN alongside it on Windows (it is advertised as self-contained but the install page lists no dependency DLLs) — unknown.
- Current (11.4) TensorRT SLA text and the 12 Aug 2025 TensorRT-RTX EULA text — not read verbatim; terms above are from the 10.x SLA, the cuDNN SLA and the April 2025 TensorRT-RTX licence snippet.
- No legal opinion found on whether NVIDIA's §2.5 "open source license" clause affects an MIT/Apache *application* that merely bundles the DLLs.
