# Keep ComfyUI's protocol, ship a sidecar, go native per model

Replacing the ComfyUI dependency with in-process inference is not one project but three, and only the first two are worth starting now. No Rust or embeddable runtime runs PhotoCraft's whole model set today: stable-diffusion.cpp (MIT, C++/ggml) is the only engine that loads Qwen-Image-Edit-2511, Krea 2, Qwen-Image-2.1, Qwen-Image-Layered and LoRAs, but it has no NVFP4 path and no published 5090 or ComfyUI-relative benchmark; candle-based Qwen-Image ports exist but stock candle bf16 ran at **0.62 s/step against ComfyUI's 0.419 s/step on the same RTX 4090**, and reaching parity took a second project of hand-written INT8/SageAttention CUDA kernels ([umag/qwen-image-rs](https://github.com/umag/qwen-image-rs)); burn's attention kernel is an open `blocker` ([burn #4325](https://github.com/tracel-ai/burn/issues/4325)); TensorRT has a first-party FLUX path (3.85 s/image FP4 on a 5090) but nothing for Qwen-Image or Krea 2 ([NVIDIA](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/)). On the NVFP4 question the answer is a qualified no: it accelerates the DiT's GEMMs by 1.6–2.6× over FP8 on a 5090, which becomes 1.2–1.8× per image because attention, text encoder, VAE and dispatch are untouched, it does nothing for the once-per-prompt encoder (the owner's own §5f runs: 14.1 s either way), it costs measurable quality in rough PTQ repacks (Qwen-Image LPIPS 0.437 vs FP8's 0.248, per [MESHIVEAI](https://huggingface.co/MESHIVEAI/Qwen-Image-2512-NVFP4)), and only ~15 % on Krea 2 because quality forced most layers to stay FP8 ([Comfy-Org/Krea-2 #6](https://huggingface.co/Comfy-Org/Krea-2/discussions/6)). The recommended order is: (1) harden `GenerativeBackend` as the engine-neutral trait it already is (days); (2) add an app-managed ComfyUI sidecar with uv-installed Python, ephemeral loopback port and job-object lifetime, which gives zero-setup without touching the GPL boundary (2–4 weeks); (3) embed llama.cpp for Qwen3-VL and ONNX Runtime for SAM 3.1, the two small models with mature non-Python runtimes (2–3 weeks each); (4) only then evaluate stable-diffusion.cpp behind the same trait for one DiT, gated on a same-machine benchmark against ComfyUI that nobody has published yet. A pure-Rust DiT (candle) is a 2027 research track, not a shipping plan.

## No engine runs the full model set natively, and the gap is the DiTs

The model set splits cleanly into two tiers. Qwen3-VL 4B and SAM 3.1 are solved outside PyTorch: llama.cpp merged Qwen3-VL dense and MoE on 2025-10-30 with official Qwen GGUF plus `mmproj` files ([llama.cpp #16780](https://github.com/ggml-org/llama.cpp/pull/16780)), and SAM 3 / 3.1 have community ONNX exports (encoder, text encoder, decoder as three graphs) that run on ONNX Runtime's CUDA EP ([samexporter](https://github.com/vietanhdev/samexporter); [comicbox/sam3.1-comicapp-onnx](https://huggingface.co/comicbox/sam3.1-comicapp-onnx)). The four diffusion transformers are the problem. Every Rust runtime surveyed either lacks the architectures (burn: no DiT port at all; diffusion-rs and mistral.rs: FLUX.1 only, LoRA "upcoming" or unsupported for diffusion) or runs them only through application-level code written on top of candle by single-maintainer projects with 1–54 stars ([EricLBuehler/diffusion-rs](https://github.com/EricLBuehler/diffusion-rs); [mistral.rs guide](https://ericlbuehler.github.io/mistral.rs/guides/models/use-image-generation/); [utensils/mold](https://github.com/utensils/mold)). Candle itself has two open Blackwell issues with no maintainer response, including a 5090 failing device init with `CUDA_ERROR_COMPAT_NOT_SUPPORTED_ON_DEVICE` ([candle #2966](https://github.com/huggingface/candle/issues/2966); [candle #3358](https://github.com/huggingface/candle/issues/3358)), and its FP8 dtype cannot even be cast on CUDA because of a kernel-name mismatch open since August ([candle #3886](https://github.com/huggingface/candle/issues/3886)).

Stable-diffusion.cpp is the standout on coverage: its README lists FLUX.1/.2/.3, Krea2, Qwen Image, Qwen Image 2.1, Z-Image and the full Qwen Image Edit series including 2511 (which needs `--model-args qwen_image_zero_cond_t=true`), with GGUF Q4–Q8, LoRA "same as stable-diffusion-webui", flash attention and Windows CUDA builds ([stable-diffusion.cpp README](https://github.com/leejet/stable-diffusion.cpp); [docs/qwen_image_edit.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/qwen_image_edit.md)). Its ceiling is precision and stability: FP8 safetensors are converted to INT8 and run through cuBLAS INT8 GEMM, 4-bit is GGUF dequantised to FP16 compute, there is no NVFP4 path ([sd.cpp #1929](https://github.com/leejet/stable-diffusion.cpp/issues/1929)), Z-Image GGUF produces blank images on CUDA in an issue still open since May ([sd.cpp #1488](https://github.com/leejet/stable-diffusion.cpp/issues/1488)), and releases arrive as `master-968`-style rolling builds. The Rust bindings (newfla's `diffusion-rs`, MIT, CUDA on Windows) exist but a C++/CMake/nvcc build and ggml's abort-on-error semantics sit inside PhotoCraft's "never crash" rule, which means a sidecar process even for a "native" engine ([newfla/diffusion-rs](https://github.com/newfla/diffusion-rs)).

TensorRT and libtorch are heavier and narrower. NVIDIA's demoDiffusion covers FLUX.1 dev/schnell in FP4 on the 5090 but lists neither Qwen-Image nor Krea 2, FP8/INT8 "does not work with LoRA weights", and FP4 ONNX export needs more than 48 GB VRAM so engines must be pre-exported by NVIDIA ([TensorRT demo/Diffusion](https://github.com/NVIDIA/TensorRT/tree/release/10.13/demo/Diffusion)). TensorRT-RTX is the right size class (under 200 MB, FP8 and FP4 GEMM declared for SM 12.0) but no DiT has been run through it and one ort user measured it 2–3× slower than DirectML ([TensorRT-RTX support matrix](https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/getting-started/support-matrix.html); [pykeio/ort #532](https://github.com/pykeio/ort/issues/532)). libtorch Windows CUDA zips are 1.9–3.7 GB compressed, AOTInductor is effectively Linux-only, and `tch` pins one exact libtorch per release ([download.pytorch.org](https://download.pytorch.org/libtorch/cu130/libtorch-win-shared-with-deps-2.11.0%2Bcu130.zip); [tch-rs](https://github.com/LaurentMazare/tch-rs)). Embedding CPython + torch in-process via PyO3 is documented only for the interpreter, and a CUDA access violation in `torch.cuda.is_available()` has killed ComfyUI Desktop outright on mismatched hardware, which is exactly the failure the crash rule forbids ([PyO3 guide](https://pyo3.rs/main/building-and-distribution); [forum.comfy.org](https://forum.comfy.org/t/windows-desktop-v0-8-28-wont-start-on-amd-gpu/4379)).

## NVFP4 speeds the GEMMs, not the prompt

The honest number is that NVFP4 on a 5090 makes one component faster and leaves the rest alone. On the DiT step it is a large win: the best-controlled community benchmark (Qwen-Image-2512, RTX 5090, ComfyUI 0.37, torch 2.11 cu130, 1328²) shows **Lightning 4-step at 2.3 s NVFP4 vs 3.6 s FP8 vs 8.6 s BF16**, and 50-step CFG runs at 42.5 s vs 76.6 s, a 1.6–1.8× FP8-to-NVFP4 gain ([MESHIVEAI](https://huggingface.co/MESHIVEAI/Qwen-Image-2512-NVFP4)). For Qwen-Image-Edit-2511 the single published card reads 4 steps at 832×1280: BF16 9.80 s, FP8 6.09 s, NVFP4 3.45 s total, with per-step NVFP4 2.5× faster than FP8 but whole-prompt only 1.77× faster, because roughly 1.9–2.0 s of each run is text encoding, VAE and graph overhead that no weight format touches ([Bedovyy](https://huggingface.co/Bedovyy/Qwen-Image-Edit-2511-NVFP4)). The hardware explains the ceiling: sm_120 has native block-scaled FP4 MMA at roughly 4× the FP8 rate, and CUTLASS reaches ~81 % of FP4 peak on an sm_120 part, but a Krea 2 profile puts GEMMs at only 50 % of DiT time with attention at 41 % and norms at 9 % ([zartbot](https://zartbot.github.io/micro_arch/nvidia/sm_120/paper.html); [Krea-2 #6](https://huggingface.co/Comfy-Org/Krea-2/discussions/6)). Even an infinitely fast GEMM would cap the DiT near 2× and the prompt lower still.

The owner's own measurements agree and sharpen the picture. In `docs/comfy/benchmarks.md` §5f, swapping the 2511 text encoder to Comfy-Org's NVFP4 repack left warm edits at 14.1 s with either file, because the encoder runs once per prompt and is not the bottleneck, while it did free 3 GB; swapping Krea 2 Turbo's model to NVFP4 took warm images from 7.1 to 5.7–6.0 s, an **18 % gain with 5 GB more VRAM free**. That 18 % is the same order as Comfy-Org's own "about 15 %" for Krea 2 and is small for a reason: Kijai reports that "not all layers could use nvfp4 matmuls due to rather bad quality loss", and the first NVFP4 upload had to be re-uploaded because its layout "doesn't allow the fast nvfp4 matmuls" at all ([Krea-2 #6](https://huggingface.co/Comfy-Org/Krea-2/discussions/6)). The file format alone is not a lever; the kernel stack is: ComfyUI "only supports NVFP4 acceleration if you are running PyTorch built with CUDA 13.0", otherwise sampling runs "up to 2× slower than fp8" through a dequantise fallback ([Comfy blog](https://blog.comfy.org/p/new-comfyui-optimizations-for-nvidia)). On Ampere and Ada there is no FP4 hardware, so NVFP4 files are at best FP8 speed there.

Where NVFP4 does not help is a long list. It does nothing for attention (41 % of Krea 2's DiT time), for the Qwen2.5-VL-7B encoder pass over prompt and reference image, for VAE encode/decode, for LoRA application, or for Python dispatch, which at 5–10 µs per kernel launch across ~1,500–2,500 launches per 60-block forward is 10–35 % of a 0.4 s Lightning step ([FastUSP](https://arxiv.org/pdf/2602.10940)). It has no official 2511 diffusion-model repack (only community ones with "rough calibration"), and none for Qwen-Image-2.1 (`docs/comfy/models.md`). And it costs quality in proportion to how it was quantised: ComfyUI PTQ NVFP4 on Qwen-Image-2512 scored LPIPS 0.437 / SSIM 0.610 versus FP8's 0.248 / 0.749 and broke Korean text rendering 0/10 versus BF16's 4/10, while SVDQuant-NVFP4 (Nunchaku) and NVIDIA's FP4 QAT are metric-indistinguishable from BF16 on FLUX.1-dev (ImageReward 0.937 vs 0.953; 1.119 vs 1.118) ([MESHIVEAI](https://huggingface.co/MESHIVEAI/Qwen-Image-2512-NVFP4); [MIT Han Lab](https://hanlab.mit.edu/blog/svdquant-nvfp4); [NVIDIA](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/)). The format is fine; rough calibration is not. The right product stance is the one the fork already ships: FP8-scaled as the safe default, NVFP4 as a Blackwell-gated policy for files with an official or SVDQuant-grade repack, never arbitrary community packs.

### What actually moves a 5090, ranked by evidence

Step distillation dominates everything else. Lightning LoRAs take 40–50 steps to 4 or 8 and turn CFG off, which halves work again: on the 2512 card that is 42.5 s to 2.3 s on NVFP4, an 18× reduction that no precision change approaches ([MESHIVEAI](https://huggingface.co/MESHIVEAI/Qwen-Image-2512-NVFP4)). Caching (TeaCache, First-Block Cache) is a substitute for distillation, not a multiplier: FBC gives 1.37× on 50-step Qwen-Image and nothing at 4 steps, and TeaCache measured 0.97× in one controlled study ([LayerCache paper](https://arxiv.org/pdf/2604.16492)). Keeping the model set resident is the second lever and is memory, not compute: a 40.9 GB BF16 Qwen on a 32 GB card streams ~9 GB over PCIe every pass, which is the whole 8.6 s vs 3.6 s gap on the 2512 Lightning run; a 20 GB FP8 or 10 GB NVFP4 set avoids the cliff, and this VRAM headroom is NVFP4's more reliable win than its tensor-core rate. Third is FP8 tensor-core matmul (`--fast fp8_matrix_mult`), worth ~13–15 % on a 4090 and underlying the ~1.6× FP8-vs-BF16 step gain on the 5090; the fork's note that its "scaled file gave noise" suggests a loader or calibration mismatch worth one afternoon ([Krea-2 #6](https://huggingface.co/Comfy-Org/Krea-2/discussions/6)). Fourth is attention: FlashAttention-3 is Hopper-only, FA4's fast path needs tcgen05/TMEM that GB202 lacks, so FA2 is the ceiling on a 5090 unless SageAttention2++ (INT8 QK, "560 TOPS, 2.7× FA2" on the 5090) is installed; SageAttention3's FP4 attention is faster still with an accuracy caveat ([thu-ml/SageAttention](https://github.com/thu-ml/SageAttention); [arXiv 2505.11594](https://arxiv.org/abs/2505.11594); [flash-attn-4-sm120](https://huggingface.co/SecondNatureComputing/flash-attn-4-sm120)). Fifth, and the only one an in-process runtime uniquely owns, is the fixed ~2 s outside the sampler plus launch overhead: TensorRT's fully fused FLUX.1-schnell at 591 ms end-to-end shows what compiled TE + DiT + VAE achieves, and torch.compile with CUDA graphs took 23 % off SDXL steps on an A100 ([NVIDIA](https://developer.nvidia.com/blog/nvidia-tensorrt-unlocks-fp4-image-generation-for-nvidia-blackwell-geforce-rtx-50-series-gpus/); [PyTorch blog](https://pytorch.org/blog/accelerating-generative-ai-3/)). For PhotoCraft's interactive fills, where §6 of `benchmarks.md` records ~1.3 s per Lightning step at 512 px and 3–5 s of encoder when pixels change, that fixed cost is a bigger target than any GEMM.

## Recommended path: trait, sidecar, small models native, then one DiT on trial

The architecture already has the right seam. `GenerativeBackend` in `crates/genai/src/lib.rs` is engine-neutral (`health`, `run`, `model_files`, `prepare`, `free`) and its doc comment anticipates an in-process runtime; workflow templates are data; tests run against an in-process fake. Stage 1 is therefore housekeeping rather than architecture: make `Request` carry model slots and sampler recipe in engine-neutral terms (the sampling constants are already known exactly, such as `shift 3.1`, `euler`/`simple`, CFGNorm, 384²/1024² reference conditioning), so a second backend can consume the same request without the ComfyUI graph JSON. Estimated effort is a few days; risk is nil; the gain is that every later stage plugs in behind one `enum Backend`.

Stage 2 is the app-managed sidecar, and it is where the zero-setup win lives. Every shipping consumer product surveyed (Krita AI Diffusion, Invoke, ComfyUI Desktop) converged on the same recipe: a native launcher bundles `uv`, installs a python-build-standalone CPython (~48 MB), `uv pip install`s a pinned torch index and ComfyUI, and talks to it over loopback ([invoke-ai/launcher](https://github.com/invoke-ai/launcher); [Comfy-Org/Comfy-Desktop](https://github.com/Comfy-Org/Comfy-Desktop); [uv docs](https://docs.astral.sh/uv/concepts/python-versions/)). The runtime is ~4.85 GB before models, and a diffusers-only worker would save under 1 GB of that while re-implementing model-set memory management and the Layered/SAM/enhancer graphs the fork already has ([docs.comfy.org](https://docs.comfy.org/installation/desktop/windows)). PhotoCraft can exceed the precedents cheaply: detect the GPU from Rust via DXGI/NVML before Python starts (ComfyUI Desktop crashes in `torch.cuda.is_available()` on AMD-only machines because it does not), bind to `127.0.0.1` on an ephemeral port the parent chooses, keep the web frontend unexposed, tie the child's lifetime to a Windows job object, and pin `(torch, cuda, comfyui, comfy-kitchen)` per PhotoCraft release the way Krita v1.53.0 pins CUDA 13 / PyTorch 2.13. The GPL analysis is unchanged from today's user-installed server (exec + sockets + JSON graphs is the FSF's "separate programs" case), provided the ComfyUI copy ships with its licence text and any custom node that imports `comfy.*` lives in a separate GPL-3.0 repo, as Krita does with `comfyui-tooling-nodes` ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#GPLPlugins); [krita-ai-diffusion](https://github.com/Acly/krita-ai-diffusion/blob/main/README.md)). Estimate 2–4 weeks; the main risk is update churn, which content-addressed uv caching and per-release pins contain.

Stage 3 takes the two small models native because their runtimes are mature and the crash boundary is manageable. Qwen3-VL 4B through llama.cpp (`llama-cpp-2`/`llama-cpp-sys-4` vendor `tools/mtmd`) with the official GGUF and `mmproj` gives the prompt enhancer without a Python process ([llama-cpp-sys-4](https://docs.rs/crate/llama-cpp-sys-4/0.4.4/source/llama.cpp/tools/mtmd/README.md)); the one caveat is that Krea 2's text conditioning taps twelve hidden layers (30,720 features per token), which llama.cpp's embedding API does not expose, so the enhancer moves native but Krea 2's encoder stays in the DiT engine. SAM 3.1 through `ort` rc.14 (ONNX Runtime 1.31, prebuilt CUDA binaries with Blackwell support as of 2026-10-12, CUDA 13.2+/cuDNN 9.23+) with a re-exported FP16 encoder gives click/text selection in-process, with the SAM License text shipped and the gated weights fetched by the user ([ort rc.14](https://github.com/pykeio/ort/releases/tag/v2.0.0-rc.14); [greenjava/sam3-onnx](https://huggingface.co/greenjava/sam3-onnx)). Both should run in a child process or at least a dedicated thread with panic isolation, since ggml and ORT abort on CUDA faults. Estimate 2–3 weeks each; risk low-medium (ort is still `rc`, with an API break in rc.14).

Stage 4 is the only stage that touches a DiT, and it must be gated on a measurement nobody has published: stable-diffusion.cpp against ComfyUI on this 5090 for 2511 Lightning and Krea 2 Turbo, same resolution, steps and seed. If sd.cpp lands within ~1.3× of ComfyUI FP8 with acceptable output, it earns a `SdCppBackend` behind the trait for the "no Python installed" tier, with GGUF Q8 for 2511 and FP8→INT8 for Krea 2, pinned to a commit with a per-model regression image set. If it lands at 2× or worse, which the INT8-GEMM/FP16-dequant design makes plausible, the sidecar stays the only DiT engine and the native tier is "small models only". Estimate 3–6 weeks after a one-week benchmark; risk medium-high. A candle port (reusing qwen-image-rs or qwen3-image21, both validated to ~1e-5 against diffusers) remains the long-run pure-Rust route, but it needs sm_120-tuned INT8/FP8 GEMMs, a Blackwell attention kernel, a ComfyUI-LoRA key mapper and CUDA-graph capture that candle 0.11 cannot do, none of which exists; budget it as 3–6 months per model and start it only after Stage 4 has a baseline to beat.

## Open gaps the notes could not close

The largest gap is that no one has measured any non-PyTorch engine on an RTX 5090 for these models: not stable-diffusion.cpp, not any candle port, not TensorRT-RTX on any DiT. The Stage 4 gate exists precisely because this report cannot predict the outcome. Second, there is no independent, controlled BF16/FP8/NVFP4 benchmark of Qwen-Image-Edit-2511 on a 5090; the single community card has no VRAM figures or ComfyUI version, and the NVFP4-vs-FP8 quality study exists only for 2512 text-to-image. Third, ComfyUI's per-step Python dispatch overhead on a 5090 has never been quantified in milliseconds; the 50–150 ms per step figure is arithmetic from launch-overhead numbers, and the owner's own `/history` timing split would be the first real data. Fourth, the exact `TensorCoreNVFP4Layout` packing of ComfyUI repacks is defined only in comfy-kitchen's kernels, and nobody has checked whether it matches NVIDIA ModelOpt's, so a Rust loader for those files is tens of lines plus an unknown amount of layout reverse-engineering, and the matmul to consume them exists nowhere in Rust outside a fork for LLMs ([SceneWorks #1022](https://github.com/SceneWorks/inference/pull/1022)). Fifth, several licence texts were read from mirrors or snippets: the GPL FAQ wording came via a 2014 mailing-list quotation because gnu.org rate-limited, the TensorRT-RTX August 2025 EULA PDF would not extract, the Krea 2 PDF was not read, and the SAM 3.1 card is gated; all should be re-verified before a published build. Finally, binary sizes for candle kernels, uncompressed footprints for every NVIDIA package, whether TensorRT-RTX needs cuBLAS/cuDNN beside it, and which libtorch version `tch` 0.26 actually pins (README says 2.13.0, lib.rs says 2.11.0) are all unmeasured.

## Conclusion

The question "what would it take to go native" has a different answer for each tier of the model set, and the honest aggregate is that the ComfyUI ecosystem is the asset, not the liability: it is where NVFP4 kernels, Lightning LoRAs, day-0 model support and the Comfy-Org repacks the fork's policy depends on all land first, and every no-Python precedent (Amuse, Draw Things) paid for independence with a private conversion pipeline and lagging architecture support. What the user actually experiences as "the ComfyUI dependency" is setup friction and a visible server, both of which a managed sidecar removes in weeks while leaving the GPL boundary, the speed, and the model coverage exactly where they are. The 5090-specific insight is that the card is compute-bound on the DiT and the remaining wins are in the fixed costs around it; that argues for owning the small models (encoder, segmenter) natively first, where Rust-side control of latency is cheap and the runtimes are mature, and for treating a native DiT as an experiment with a numeric gate rather than a roadmap item.

NVFP4 deserves the same reframing. It is a memory lever that happens to be a GEMM lever, and the fork's existing `auto` policy already captures what is safely available (an 18 % Krea 2 gain and 3–5 GB of headroom). The next percentage points on this machine come from FP8 tensor-core matmul that currently produces noise, a SageAttention wheel, and the per-prompt encoder and VAE time, none of which a weight format changes. When a Rust DiT runtime does become worth building, the qwen-image-rs result is the template: the model port is weeks, the kernels are the project, and the sm_120 versions of those kernels do not yet exist anywhere in Rust.
